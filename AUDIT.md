# AUDIT — Multi-User AI Social Media Manager

**Scope:** end-to-end pipeline integrity + every point where information is lost.
**Method:** 5 parallel read-only deep-dives (code only, no live execution). All refs are `file:line`.
**Status:** Findings only. No changes made.

## 1. WebChat flow + intent detection
- Public assistant (`src/routes/assistant.ts`): 500-char cap, 20/min IP rate limit. High-risk prompt-injection surface via webchat + raw WhatsApp text.
- Chat API (`src/routes/chat.ts`): `GET /api/chat/messages`, `POST /api/chat` — no payload size/type validation on attachments; message stored as typed.
- `AssistantService.ts`: 30s `answerCache` — a cached response is served even if a queued system message arrived seconds earlier (stale-intent risk).
- Intent: `generate.ts:239 extractIntent` → `planContent:251` → `writeContent:259` → `brandCheck:270` → `generateImagePrompt:282` → `generatePlatformContent:325` → `generateFullDraft:339`. Extraction depends on a well-formed `transcript`; short webchat messages degrade it.

## 2. Post creation
- `runPipeline`/`handleUserInput` state machine drives creation through `AWAITING_*` stages (`conversation.ts:851,1087`).
- **Info loss:** `intent.platform` is never populated — the platform a user explicitly chose is not recorded anywhere.
- **Info loss:** empty `imagePath`/`imageUrl` after image generation failure — publish proceeds with an empty URL instead of gating.
- Edits stored in `postEdits` but never folded back into the live record used at publish time.

## 3. Caption generation (highest-severity cluster)
- **`publish.ts:122,169` prefers `platformContent` over edited base `content`** — but every edit path (`conversation.ts:887,1041-1050`) only patches the base caption. Result: **the caption the user approved is NOT the caption that publishes.**
- **`caption.ts:7-9` `platformCaption()` ignores its `platform` argument** — dead parameter; per-platform text is identical.
- `brandCheck.fixedCaption` (`conversation.ts:887,1050`) patches only base content, never `platformContent`.
- Single-platform users see one caption in preview but another publishes (`conversation.ts:832-839` vs publish).
- **Full-regenerate / full-edit (`conversation.ts:1029-1033`) discards `editRequest` and re-runs from the original transcript** — user instructions lost.
- Caption preview logged to chat is sliced to 200 chars (`whatsapp.ts:127`) — user can't see/approve full caption in chat.

## 4. Hashtag generation
- **Schema mismatch:** pipeline types hashtags as a space-joined string, but LLM prompts/schemas demand arrays → `chatJson` returns arrays that get `join(',')` or raw-array-typed against a string. Output is non-deterministic (`llm.ts`, `generate.ts`).
- **`seoKeywords` are generated but never used** anywhere downstream.

## 5. Scheduling / time parsing
- `normalizeScheduleTime` (`publish.ts`) + NL-time parse in `conversation.ts:573,599` — **all local-language times parsed as UTC.**
- `POST /api/posts/schedule` / cancel / reschedule endpoints are inline in `server.ts:322-458`.
- **`parseScheduleTime` accepts degenerate input like "2026"** as a valid date.
- `plan.suggestedTime` generated by the plan stage is never surfaced/used.

## 6. Timezone handling
- **No per-user timezone.** Dashboard `datetime-local` values are naive strings; server interprets in server-TZ, reschedule interprets in browser-TZ (`Scheduled.tsx:255` vs `:188`) → inconsistent schedule times across the same app.

## 7. Dashboard settings
- Dead settings keys read only by status endpoints, never by logic: `payment_method_local`, `payment_local_auto`, `payment_local_details`, `stripe_webhook_url`, `instagram_token` (and related).
- `meta_config` dead keys: `whatsapp.welcome_template*`, `meta_ads.ad_account_id`, `meta_ads.access_token` (no reader).
- **`UserPreferences.language/tone/audience/brandVoice` are read by the pipeline but have no write API or UI** — preference silently ignored.
- `JobQueue` is fully implemented but never started anywhere.

## 8. Meta Ads flow
- `adConversation.ts`: `launchAdCampaign`; **`websiteUrl` is lost between steps** (not carried into the final campaign object).
- **`adDataSummary` (`conversation.ts:395-407`) omits currency, budgetType, startDate, endDate** — classifier cannot see them, so it re-prompts for already-given data.
- **Ad scheduler double-launch race** (`adConversation.ts:245-249`): no `processing` guard before launching; overlapping runs can create two campaigns.
- **Campaigns stuck in `creating` after a crash are never recovered** — no recovery path exists.
- Ad preview image uses a **15-min TTL signed URL stored in the DB row** → link dies after 15 minutes.
- **`getMissingAdFields` ignores websiteUrl/currency/dates.**
- Dead WhatsApp "Schedule" button in ad flow — no handler (`webhook.ts:27-106`).

## 9. Chatbot tools/actions
- Tools are plain `switch`/decision branches in the conversation pipeline — no registry, no tool catalog, no permission model per tool.
- `sendDecision` sends `question ?? reply` (`conversation.ts:688`) — when both exist, the **reply is dropped**.
- If `classify()` throws, the entire decision is discarded into an `unclear` fallback (user input effectively lost).

## 10. Backend APIs
- Route inventory (from `server.ts` + `src/routes/*`): auth (login/register/verify/clerk), chat (GET/POST), assistant, posts (CRUD, schedule/cancel/reschedule, `?pending`), uploads, meta (ads), admin (settings, meta-settings, stats, users, package pause/resume), webhook (WhatsApp + gateway). Full inline list is in `server.ts:322-458` + route dirs.
- No global error envelope; partial-failure semantics vary by endpoint.

## 11. DB saves / persistence
- 28 tables (`src/db/schema.ts`): users, sessions, conversations, messages, posts, postEdits, scheduledPosts, adCampaigns, metaConfig, adminConfig, userPreferences, brandProfile, notifications, webhookEvents, jobQueue, etc.
- **`setConversation` replaces the whole record (`store.ts:749-761`)** — every transition drops `intent`/`adData`/`step` not re-passed by the caller (~40 call sites) → mid-flow info loss.
- `logMessage` (~`store.ts:720`), `createNotification` (~`store.ts:1781`), `logWebhookEvent` added Phase 5.
- **`webhookEvents.headers` is never populated** (always null).

## 12. Scheduler execution
- `startScheduler` (`publish.ts:434`) selects due rows by `status='pending' AND publishAt <= now`.
- **`publish.ts:452` marks the row `completed` right after an un-awaited `enqueuePublish`** — crash in that gap loses the job; recovery skips completed rows → permanent loss.
- `recoverStuckScheduledPosts` (store.ts) rescues stale `processing` → `pending` but cannot see the gap above.
- **Scheduled content is a live reference, not a snapshot** — editing a scheduled post after scheduling changes what later publishes.

## 13. AI instructions / schema
- Prompts live in `llm.ts` (chatJson/chat) + `generate.ts`. Schemas typed by hand; several drift from actual pipeline expectations (hashtags, entity index, adSummary keys).
- `d.intent` sparsely populated by fallback paths bypasses the SYSTEM_INTENT extractor → weak intent on short messages.
- Entity index: last 5 items × 60 chars; chat history: last 12 msgs × 300 chars (`conversation.ts:488-547`) — context truncation is aggressive.
